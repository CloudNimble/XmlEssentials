# XSD source generation

Part of the [XmlEssentials spec](README.md).

XSD is a **compile-time** front-end to the [serializer generator](10-source-generation.md). It is not a runtime validator.

```text
*.xsd  →  POCOs + our attributes + [XmlSerializable]
       →  existing generator emits AOT Serialize/Deserialize
```

No `XmlSchemaSet`. No `XmlUrlResolver`. No schema documents on the Native AOT publish graph. The published binary knows types, not `.xsd` files.

## Input

MSBuild `AdditionalFiles` with `*.xsd` (and `*.wsdl` **ignored** — WSDL is out of scope). `xsd:include` / `xsd:import` resolve **only** to other AdditionalFiles in the same compilation, by file name or relative URI that maps to an AdditionalFile. Network, `file://` outside the compilation, and DTD inside a schema document are **errors** (XMLXE010).

```xml
<ItemGroup>
  <AdditionalFiles Include="Schemas\**\*.xsd" />
</ItemGroup>
```

Optional MSBuild metadata:

```xml
<AdditionalFiles Include="Schemas\order.xsd">
  <XmlEssentialsNamespace>MyApp.Xml.Order</XmlEssentialsNamespace>
  <XmlEssentialsContext>OrderXmlContext</XmlEssentialsContext>
</AdditionalFiles>
```

Defaults: C# namespace = root namespace + `.Generated`; context name = `{FileName}XmlContext`.

## Output (same compilation)

For each schema (and its includes/imports):

1. One `partial` class per global `xs:element` / `xs:complexType` (element-first like `xsd.exe`; complex types used only as named types become classes too).
2. Our mapping attributes: `[XmlRoot]`, `[XmlElement]`, `[XmlAttribute]`, `[XmlArray]` / `[XmlArrayItem]`, `[XmlText]`, `[XmlNamespaceDeclarations]`, nillable → `XmlNilHandling` / nillable members.
3. `xs:choice` / substitution groups → `[XmlDerivedType]` + `[XmlPolymorphic]` (not BCL `[XmlInclude]`).
4. `xs:simpleType` restrictions → CLR type + converter where needed (enumerations → enum; patterns are **not** validated at runtime unless a converter is generated that enforces them — default: map to `string` and do not emit a regex validator; AOT must not pull `Regex` unless the consumer asked).
5. A `partial` `XmlSerializerContext` with `[XmlSerializable(typeof(T))]` for every generated root and reachable type.
6. XML doc comments from `xs:annotation` / `xs:documentation`.

Generated files use a stable header (`// <auto-generated />`) and are **not** user-edited. Users extend with another `partial` in their own files.

The serializer generator in the **same** analyzer DLL sees these types in the compilation (they are emitted before or in a second generator pass). Order: XSD generator runs as `IIncrementalGenerator` producing syntax; the context generator’s syntax provider includes generated `[XmlSerializable]` types. If two generators in one assembly need a sequence, use two `IIncrementalGenerator` classes in `CloudNimble.XmlEssentials.SourceGeneration` — XsdGenerator and SerializerGenerator. SerializerGenerator must accept types from the current compilation **including** generated ones (Roslyn does; generated syntax is in the compilation for subsequent generators in later pipelines — **do not** rely on same-pass visibility). Practical contract: XSD generator emits the POCOs + context **source**; the next compilation (or the serializer generator consuming `AdditionalTexts` + producing types that the serializer also walks via `ForAttributeWithMetadataName` after the first generator adds them) must work in `dotnet build`. If same-build visibility is insufficient, emit `[XmlSerializable]` as part of the XSD generator’s **own** serialization stubs is forbidden — keep one ser/deser emitter. Roslyn runs all incremental generators and then compiles combined output; **one build** is enough if SerializerGenerator uses `SyntaxProvider` on compilation after all generators… actually in Roslyn, generators cannot see each other’s output in the same compilation. **Contract:** the XSD generator emits POCOs **and** a partial context with `[XmlSerializable]`. It **also** invokes the same emit helpers the serializer generator uses for those types, **or** the consumer adds a **hand-written** partial context that lists `[XmlSerializable(typeof(Generated.Foo))]` in a second compilation.

**Chosen contract (AOT-safe, one `dotnet build`):** one analyzer DLL, two generator classes. The XSD generator emits:

- POCO syntax
- a `partial` context class with `[XmlSerializable(typeof(...))]` attributes
- **and** the `XmlTypeInfo` / serialize-deserialize implementation for those types, by calling shared emit APIs in the analyzer (not a second generator looking at the first’s output)

Hand-written contexts that reference generated types still go through SerializerGenerator as today. Generated contexts do not depend on SerializerGenerator seeing XSD output.

## AOT

| Rule | Why |
| --- | --- |
| No `.xsd` in the published app | Trimmer/ILC would have nothing useful to do with them; loading schema at runtime is reflection + URL resolve. |
| No `System.Xml.Schema` | Forbidden reference, same as other BCL XML. |
| Every generated type is in a context | Native AOT uses context overloads only. |
| Closed world | `xs:any` → `[XmlExtensionData]` / `XmlElementNode` list, not `object` + runtime type load. `xsi:type` values are the `[XmlDerivedType]` set from the schema, not `Type.GetType`. |
| No `XmlUrlResolver` / HTTP in the generator | Schemas must be AdditionalFiles. Build is offline. |
| `PublishAot=true` smoke test | Test asset includes a small `.xsd`, generates types, serializes via `Default` context. |
| Reflection disabled in that test | `IsReflectionEnabledByDefault=false`. |

## Mapping notes

| XSD | C# |
| --- | --- |
| `xs:string` etc. | CLR + [lexical rules](02-xml-fidelity.md) |
| `xs:nillable` | nillable member; write `xsi:nil` |
| `maxOccurs="unbounded"` | `List<T>` unwrapped unless `xs:sequence` wrapper name differs — then `[XmlArray]` |
| `xs:attribute` | `[XmlAttribute]` |
| `xs:anyAttribute` | `[XmlExtensionData]` attribute bag |
| `xs:any` | `[XmlExtensionData]` element bag / `List<XmlElementNode>` |
| substitution group | `[XmlDerivedType]` on the head |
| `xs:extension` of complex type | CLR inheritance; **default** member order is base then derived. `[XmlPropertyOrder]` is **not** auto-emitted (schema sequence is per type, which matches default walk). |
| anonymous complex type | nested class named `{Parent}_{Element}` |

## Diagnostics

- XMLXE010: include/import not in AdditionalFiles, or DTD in a schema document
- XMLXE011: unsupported construct (`xs:redefine`, `xs:notation`, identity constraints as runtime checks — identity constraints are **ignored** with XMLXE011 **info**, not error; `xs:key` does not emit runtime validation)
- XMLXE012: name collision in generated C#
- XMLXE013: invalid XML name for a generated member

## Non-goals (this generator)

- Validating an instance document against the schema at runtime
- WSDL / SOAP bindings
- Emitting `System.Xml.Serialization` attributes
- Downloading schemas

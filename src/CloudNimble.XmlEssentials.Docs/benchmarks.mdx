## How to read these tables

Each table compares the same work done by two or three libraries.

- **Time** is the mean time for one operation. A microsecond (µs) is 1,000 nanoseconds (ns).
- **Allocated** is the managed memory one operation allocates. Less memory means fewer garbage collections under load.
- **Faster** is the `System.Xml` time divided by the XmlEssentials time. "2.4×" means XmlEssentials does the work in well under half the time.

`System.Xml` is the baseline: `XmlReader`, `XmlWriter`, `XmlDocument`, and a cached `System.Xml.Serialization.XmlSerializer`. System.Text.Json appears beside it as a yardstick for what a modern .NET serializer achieves. It reads and writes JSON, not XML, so it isn't doing the same job.

## Read real documents

The reader walks every token of four real files and keeps whitespace and comments. These files come from other parsers' test suites, and none of them was written for this library.

| Document | System.Xml `XmlReader` | XmlEssentials `Utf8XmlReader` | Faster |
| --- | --- | --- | --- |
| Word document (WordprocessingML, 11 KB) | 19.1 µs / 25,144 B | 14.7 µs / 944 B | 1.3× |
| RPM package metadata (21 KB) | 30.8 µs / 20,064 B | 17.7 µs / 80 B | 1.7× |
| OpenDocument text (57 KB) | 79.3 µs / 56,017 B | 49.9 µs / 6,952 B | 1.6× |
| RSS feed (198 KB) | 194.0 µs / 47,137 B | 84.6 µs / 1,441 B | 2.3× |

The few bytes XmlEssentials allocates are per reader, not per token: buffers for decoded values and for documents with more than eight attributes or namespaces on one element. Pass the reader a scratch buffer and all four files read with **0 bytes** allocated, in the same time. See [Use Utf8XmlReader](/guides/use-utf8xmlreader).

## Parse into a DOM

Each library parses the whole file into its document object model.

| Document | System.Xml `XmlDocument` | XmlEssentials `XmlDocument` | Faster |
| --- | --- | --- | --- |
| Word document (11 KB) | 51.6 µs / 127,176 B | 21.2 µs / 104 B | 2.4× |
| RPM package metadata (21 KB) | 70.6 µs / 170,953 B | 25.1 µs / 104 B | 2.8× |
| OpenDocument text (57 KB) | 190.5 µs / 353,889 B | 66.9 µs / 105 B | 2.8× |
| RSS feed (198 KB) | 333.9 µs / 709,082 B | 114.3 µs / 105 B | 2.9× |

The 104 bytes are the document object. Everything else lives in pooled buffers that go back to the pool when you dispose the document, which is why the number doesn't grow with the file. `System.Xml` allocates one object per node.

## Small documents

Small payloads show the fixed cost of each API: what you pay before the first byte is read or written. The tiny document is `<root id="1"><n>42</n></root>`. The catalog has 200 items.

| Operation | System.Xml | XmlEssentials | Faster |
| --- | --- | --- | --- |
| Write the tiny document | 327 ns / 7,328 B | 58 ns / 0 B | 5.6× |
| Read the tiny document | 328 ns / 2,472 B | 65 ns / 0 B | 5.0× |
| Parse the tiny document into a DOM | 642 ns / 5,176 B | 115 ns / 104 B | 5.6× |
| Write the catalog | 33.0 µs / 13,728 B | 22.7 µs / 0 B | 1.5× |
| Read the catalog | 25.8 µs / 15,088 B | 20.2 µs / 0 B | 1.3× |
| Read the catalog and parse its integers | 29.7 µs / 35,808 B | 19.3 µs / 0 B | 1.5× |
| Parse the catalog into a DOM | 52.7 µs / 136,128 B | 30.1 µs / 104 B | 1.7× |
| Navigate the parsed catalog | 3.5 µs / 0 B | 2.8 µs / 0 B | 1.3× |

`System.Xml` allocates 7 KB to write a 30-byte document because every `XmlWriter` starts with its own buffers. A `Utf8XmlWriter` writes straight into your buffer, and you can reuse one writer with `Reset`.

| Read 1,000 orders | 788.0 µs / 567,319 B | 327.3 µs / 249,075 B | 418.7 µs / 248,603 B | 1.9× |
| Write 1,000 orders | 414.2 µs / 214,507 B | 204.1 µs / 314 B | 242.6 µs / 0 B | 1.7× |

When XmlEssentials reads objects, the memory it allocates is the objects and strings it gives you back. When it writes into your buffer, it allocates nothing.

### Source generation

A [source-generated context](/guides/source-generation) needs no reflection, which makes it safe for trimming and Native AOT. It has a write fast path, and it reads with the same engine as the reflection resolver.

| Operation | System.Xml | XmlEssentials, reflection | XmlEssentials, source generation |
| --- | --- | --- | --- |
| Read a customer | 8.9 µs / 16,496 B | 3.3 µs / 3,168 B | 3.1 µs / 3,104 B |
| Write a customer | 4.2 µs / 8,648 B | 1.7 µs / 0 B | 1.3 µs / 0 B |

The first call for a type through reflection costs about 0.6 ms while the serializer builds the type info for that type and options instance. Every later call with the same options uses the cached type info. See [Reflection vs. source generation](/guides/reflection-vs-source-generation#what-each-approach-costs).

## How XmlEssentials compares with System.Text.Json

XmlEssentials has the same API shape as System.Text.Json, so it's fair to ask whether it has the same speed. It's close, and it isn't equal. In the tables above:

- **Ahead** on the objects of three derived types (read 113 µs against 146 µs, write 73 µs against 82 µs). Each library writes them in its default shape: XmlEssentials names each element for its type, and System.Text.Json writes a `$type` property.
- **Behind** on the other rows, by 1.07× to 2.2×. The widest gaps are single values: 55 ns against 25 ns to read an `int`.
- **Equal or lower in memory** on most rows.

XML asks more of a parser than JSON does. `<int>1</int>` is three tokens, and the name has to match at both ends; in JSON, `1` is one token. Reading those three tokens takes the XmlEssentials reader alone longer than System.Text.Json takes for the whole value, so a single XML value can't be read as fast as a JSON one. What you get instead is XML at a cost close to JSON's.

## How the benchmarks are run

- [BenchmarkDotNet](https://benchmarkdotnet.org) 0.15.8, `ShortRun` job with the in-process toolchain, .NET 11.0 on x64, Windows 11 on an Intel Core Ultra 9 285K (run under Hyper-V on 2026-11-23).
- Each library reads the document it wrote itself, and each side keeps the same whitespace and comments.
- The `System.Xml` serializer and its reader and writer settings are created once and reused, which is the fastest way to use them. XmlEssentials writers are reused with `Reset`.
- The 0 B results are also enforced by unit tests that measure allocated bytes, so they can't drift without a test failing.
- Times move by 5% to 8% between runs on this machine. Compare the ratios, not the last digit.

## Run the benchmarks yourself

<Steps>
  <Step title="Clone the repository">
    ```bash
    git clone https://github.com/CloudNimble/XmlEssentials.git
    cd XmlEssentials/src
    ```
  </Step>
  <Step title="Run every benchmark">
    ```bash
    dotnet run -c Release --project CloudNimble.XmlEssentials.Performance -f net11.0 -- --filter "*"
    ```

  </Step>
  <Step title="Or run one group">
    ```bash
    dotnet run -c Release --project CloudNimble.XmlEssentials.Performance -f net11.0 -- --filter "*RealDocumentBenchmarks*"
    ```

    The groups are `RealDocumentBenchmarks`, `Utf8XmlReaderBenchmarks`, `Utf8XmlReaderFlowBenchmarks`, `Utf8XmlWriterBenchmarks`, `Utf8XmlWriterStyleBenchmarks`, `XmlDocumentBenchmarks`, `XmlNodeBenchmarks`, `XmlSerializerBenchmarks`, `XmlSerializerFeatureBenchmarks`, `XmlSerializerGraphBenchmarks`, `XmlSerializerObjectBenchmarks`, `XmlSerializerObjectSequenceBenchmarks`, `XmlSerializerSequenceBenchmarks`, and `XmlSerializerSourceGenBenchmarks`. The tables on this page come from `RealDocumentBenchmarks`, `Utf8XmlReaderBenchmarks`, `Utf8XmlWriterBenchmarks`, `XmlDocumentBenchmarks`, `XmlSerializerBenchmarks`, `XmlSerializerObjectBenchmarks`, and `XmlSerializerGraphBenchmarks`.
  </Step>
  <Step title="Read the results">
    BenchmarkDotNet writes a Markdown table for each group to `BenchmarkDotNet.Artifacts/results`.
  </Step>
</Steps>
